# PR #126 CI efficiency: measured findings and safe changes

**Baseline research reviewed:** 2026-10-26. This records the pipeline before the follow-up implementation in [canonical CI](../runbooks/ci-canonical.md). Research only; no workflow, application, settings, publication or deployment changes. Source inspected at `d701a9732a9b00b982482accd85cd648b88241c7`; merge `9aee29cf45644c64bf1402bf42849b7c66eb0f59` supplied by the task owner. Main CI monitoring remains with the owner.

## Finding

The final PR CI took **19m03s elapsed**, with **52m27s summed job time** across parallel runners. Its critical job was `cms-browser` at **18m40s**, dominated by a **9m32s browser prerequisite installation**, including **9m15s downloading 25.9 MB of Ubuntu packages**. Next compilation itself took **55s**. The second bottleneck was `cms-test`: **12m01s total**, including **10m08s Vitest**. There are real setup and database-initialization efficiencies available; removing security checks or packaged-image verification is unnecessary. [Final browser job](https://github.com/Optidigi/siteinabox/actions/runs/40407967347/job/121870522186), [final test job](https://github.com/Optidigi/siteinabox/actions/runs/40407967347/job/121870522543).

Repeated qualification amplified the wait: these four runs consumed **157m28s summed job time**, of which **105m01s** preceded the final green run. Those earlier costs include successful work alongside failures and cancellation; they are not all avoidable. These are four distinct runs/heads, each attempt 1, rather than four retries of identical source.

## What the slow steps actually did

**Browser lane.** Final step breakdown from the [job log](https://github.com/Optidigi/siteinabox/actions/runs/40407967347/job/121870522186):

| Work | Time |
| --- | ---: |
| Runner setup, PostgreSQL container initialization, checkout, pnpm/Node setup | 41s |
| Frozen dependency install | 8s |
| DNS tooling installation | 50s |
| Playwright `install --with-deps chromium` | 572s |
| Payload type generation | 4s |
| Invitation action production build + boundary checks | 118s |
| Built CMS/browser/renderer journey | 260s |
| Checkout browser contract | 53s |
| Invitation/browser evidence upload | 2s + 7s |
| Container teardown + other timestamp gaps | 5s |

The slow install fetched Ubuntu packages from `azure.archive.ubuntu.com` at **46.7 kB/s** (21:54:13 approximately through 22:03:28). Chromium, FFmpeg and headless shell downloads followed at 22:03:32–22:03:42. The previous advisory-failure run showed the same issue: **9m40s APT transfer at 44.8 kB/s**, in a 594-second install step. By comparison the test-failure run installed everything in **22s**, with APT transfer **5s at 4,959 kB/s**. This establishes a network/package-install bottleneck; it does not establish a permanent mirror fault. The final renderer lane also spent **308s** installing its browser, versus **7s building** and **25s analytics browser testing**. [Earlier browser job](https://github.com/Optidigi/siteinabox/actions/runs/40402078747/job/121850891839), [slow previous install](https://github.com/Optidigi/siteinabox/actions/runs/40404485218/job/121858585925), [final renderer job](https://github.com/Optidigi/siteinabox/actions/runs/40407967347/job/121870522562).

Within invitation verification, Next's optimized build began 22:03:57, compilation finished 22:04:51 (**55s reported**), page-data collection began 22:05:20, static generation finished 22:05:25, and the action checks passed 22:05:34. Compilation is only one part of the 118-second step. The following browser command **already reuses that CMS build** via `--reuse-built`; it does not compile CMS a second time. It initializes its own fixture, builds the renderer, starts real production processes, exercises sessions/auth/tenant denials/save/publication/legal journeys, restarts those artifacts, and audits/redacts evidence. The renderer reports **1.19s build time** at 22:06:08–22:06:10; fixture completion is logged at 22:06:01 and full journey completion at 22:10:06. Roughly **236s after renderer compilation** remains for process startup, browser journeys, restart and evidence checks, not compilation. Exact per-journey attribution is unavailable without added phase instrumentation. [Invitation driver](https://github.com/Optidigi/siteinabox/blob/d701a9732a9b00b982482accd85cd648b88241c7/apps/cms/tests/security/invitation-actions.mjs), [browser driver](https://github.com/Optidigi/siteinabox/blob/d701a9732a9b00b982482accd85cd648b88241c7/apps/cms/tests/browser/built-app-browser.mjs).

The browser's HTTPS tunnel is an **owned loopback HTTP CONNECT proxy**, with explicit permitted authorities. There is no external tunnel provisioning in this driver. Its startup is not separately timed; blaming minutes on tunnel negotiation is unsupported. Renderer builds elsewhere (renderer quality, image verification) serve different environments/proofs; cross-job reuse would require matching build inputs. Saving this journey's tiny renderer compilation alone will not materially fix the critical path. [Tunnel implementation](https://github.com/Optidigi/siteinabox/blob/d701a9732a9b00b982482accd85cd648b88241c7/apps/cms/tests/browser/built-app-tunnel.mjs).

**CMS suite.** Final [test job](https://github.com/Optidigi/siteinabox/actions/runs/40407967347/job/121870522543): PostgreSQL initialization **20s**, checkout/tool setup **22s**, pnpm install **5s**, DNS installation **30s**, prerequisite browser **20s**, types **3s**, commerce release checks **6s**, Vitest step **608s**, and **7s** other setup/cleanup/gaps. Vitest internally reports **605.23s**, **357 files / 2,746 tests passed**, with transform **7.01s**, setup **129.06s**, import **129.06s**, tests **289.89s**, environment **11.28s**. These reporter categories are not independently removable wall time; migrations executed inside hooks overlap the tests category.

The log contains **3,801 completed migration messages**, **152 distinct migration names**, and **25 executions of the initial-schema migration**. Summing each logged migration's own milliseconds yields **114.263s**, excluding drops, import/startup, bookkeeping and fixture operations. The prior two full suites likewise show 3,801 messages, with **77.035s** and **112.448s** migration execution. This is measured repeated schema initialization, not just a speculative fixture problem. The helper's comment that one worker means one migration initialization per `pnpm test` is contradicted by these logs. `getTestPayload()` caches a module-local instance but calls `dropDatabase()` and committed migrations on a cache miss; the config serializes files with `maxWorkers: 1` and `fileParallelism: false` while retaining default isolation. Do not turn off isolation globally: these suites mutate database/schema, environment and mocks. Some repeated migrations are explicit migration-rehearsal coverage. The exact safe-to-amortize subset needs a benchmark. [Config](https://github.com/Optidigi/siteinabox/blob/d701a9732a9b00b982482accd85cd648b88241c7/apps/cms/vitest.config.ts), [integration helper](https://github.com/Optidigi/siteinabox/blob/d701a9732a9b00b982482accd85cd648b88241c7/apps/cms/tests/integration/_helpers.ts), [guarded setup](https://github.com/Optidigi/siteinabox/blob/d701a9732a9b00b982482accd85cd648b88241c7/apps/cms/tests/setup.ts). Vitest documents per-file isolation, repeated setup/import costs, and file-based sharding with merged reports. [Official performance guidance](https://vitest.dev/guide/improving-performance.html).

## Why four cycles were needed

1. Initial generation failed in cms-quality in **3s** with the `server-only` import exception; cms-test generation and the Docker build hit the same exception. Source dependency review separately rejected changed graph/configuration needing fresh review. The browser lane spent **435s** in prerequisite installation before cancellation; it never reached browser qualification. [Generation failure](https://github.com/Optidigi/siteinabox/actions/runs/40400896343/job/121846130238), [source review failure](https://github.com/Optidigi/siteinabox/actions/runs/40400896343/job/121846131563).
2. Next full suite ran for **603s** before failing **10 tests in four files**: `cms-agent-route`, `setTenantTheme-access`, `tenant-theme-route` had incomplete `payload.findByID` doubles; `route-navigation-parity-source` had a stale source assertion. Successful image/browser work still ran concurrently. This is a strong case for focused fixture regressions before another broad cycle, while retaining the authorization assertions. [Test failure](https://github.com/Optidigi/siteinabox/actions/runs/40402078747/job/121850892109).
3. Then all upstream lanes passed, but `required-ci` rejected **new/changed `image:cms-cloudflared` advisory `CVE-2026-111943`, stdlib `v1.27.2`**, requiring review. The aggregate failed near minute 18 although image-CMS finished near minute 5:20, because it waits for every job. This was a functioning security gate. [Aggregate failure](https://github.com/Optidigi/siteinabox/actions/runs/40404485218/job/121866920790).
4. Final green used changed reviewed inputs and repeated full qualification. Across the four runs, elapsed durations sum to **59m33s**, but runs overlap, so this is not calendar wait. First creation to last job completion spans **69m17s**, including gaps between runs; the evidence does not attribute those gaps to human work, review or tooling.

## Ranked plan, preserving required proof

1. **Remove the slow OS dependency installation from the hot path.** Benchmark a digest-pinned, reviewed browser-ready runner/container against current runners, ensuring exact Node/pnpm/Playwright versions, fonts, DNS tools, PostgreSQL ownership, networking and sandbox behavior remain valid. Record APT/browser download phases separately. Browser-binary caching alone targets the wrong work: Playwright explicitly notes Linux OS dependencies cannot be solved by its browser cache and generally discourages binary caching. [Official Playwright CI guidance](https://playwright.dev/docs/ci#caching-browsers). **Inference:** replacing the final 572s install with the observed 22s would shorten browser time by **9m10s**, but total CI would then be constrained by the unchanged **12m01s CMS test job**: approximately **12m24s** end-to-end, a **6m39s** improvement. That is a counterfactual calculation, not a promised runtime. Benchmark cold image pull and font/rendering parity before adoption.
2. **Split pure unit work from guarded DB integration; benchmark 2–4 integration shards.** Give every shard its own freshly authorized database/service and worker storage; keep destructive migration rehearsals independently isolated. Retain prerequisite validation, real migrations, tenant/auth tests, teardown and provider doubles in every applicable shard. Use duration-balanced allocation, verify every file is covered exactly once, merge reports, and require every shard's success in the aggregate. One shared database with more workers is unsafe. Revisit repeated migration setup only after explicit per-file state/reset analysis; do not replace real migrations with schema push. **Inference:** balanced 2–4-way execution could bring the 608s suite portion into roughly **180–360s**, plus setup and reporting; no speedup has been benchmarked, and extra runners increase setup/cost. [Official Vitest sharding](https://vitest.dev/guide/improving-performance.html#sharding).
3. **Catch known failures before full qualification, and surface advisory failures as soon as images finish.** Extend existing `check:preflight` / `check:affected --plan` usage with generator import validation and focused changed-auth-route/mock/source-parity tests. Evaluate an early image-evidence security check dependent only on image/source lanes, while retaining final `required-ci` and its complete success/evidence checks. In the advisory run this could expose the blocker around **5–6 minutes** rather than minute 18 (**inference**, not measured implementation). Do not make new findings warnings, cache old dispositions as fresh, or treat diagnostic receipts as qualification. Cancel obsolete PR runs as already configured; any fail-fast cancellation must leave required CI unsuccessful and retain available failure evidence. Avoid a global serial preflight that adds latency without saving useful work. [Existing fast-feedback contract](../runbooks/fast-feedback.md), [verification matrix](../verification-matrix.md).
4. **Reuse verified main image bytes instead of rebuilding twice, through an explicit policy change.** Canonical CI on main builds all three images. Path-selected standalone `build-{cms,renderer,site}-image.yml` workflows invoke the same verifier again, retaining **TAR + JSON archives**, whereas CI retains **JSON only**. This duplication is intentional under current release policy: publication accepts a successful main standalone archive run, validates exact source/run/attempt/archive/image/security evidence and owner approval, then promotes those bytes **without rebuilding**. A PR merge-ref archive is not an eligible main archive, and site CI's synthetic analytics token can mark it unpublishable. [CI workflow](https://github.com/Optidigi/siteinabox/blob/d701a9732a9b00b982482accd85cd648b88241c7/.github/workflows/ci.yml), [standalone CMS archive workflow](https://github.com/Optidigi/siteinabox/blob/d701a9732a9b00b982482accd85cd648b88241c7/.github/workflows/build-cms-image.yml), [publication policy](../runbooks/image-publication.md).

   A safe design would have a single **trusted main exact-SHA producer** retain eligible verified archives, with narrowly validated consumers and updated publication/aggregate policy tests. Preserve real packaged smokes, source and runner provenance, run/attempt, raw archive hashes, image ID/platform/native checks, fresh advisory review, protected owner approval, seven-day verification retention, 90-day publication receipts and fail-closed expiry behavior. Cross-run downloads need an explicit run identifier/token; GitHub's transport digest warning does not replace the repository's hard hash/provenance checks. [Official artifact sharing/validation](https://docs.github.com/en/actions/tutorials/store-and-share-data). **Inference:** avoiding a duplicate set could save roughly **5–12 runner-minutes** when all three are selected, anchored to the final CI matrix's **11m30s** summed job time; actual standalone upload time, inputs and scheduling are unmeasured. This mainly reduces main compute, not the observed PR critical path. Do not enable registry-cache publication or elevate PR permissions.
5. **Cache expensive inputs selectively; select diagnostic checks conservatively.** pnpm caching already exists and final frozen installs took **5–9s per quality/image lane**; prioritizing more dependency caching has little measured upside. Benchmark `.next/cache` (compiler intermediates, not completed qualification receipts) with OS/architecture, Node/pnpm, lockfile, Next version and relevant inputs in keys. Treat restored cache as untrusted and preserve regeneration on miss. Container layer caching and pinned scanner binary/advisory DB caching are candidates only after phase measurements; reverify scanner hashes/publisher facts and refresh advisory data under existing freshness limits. [Official Next CI cache guidance](https://nextjs.org/docs/app/guides/ci-build-caching), [GitHub cache security](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching).

   Existing affected-check selection is **local preflight**, with shared/unknown changes selecting all owners. It cannot currently skip canonical jobs/images: `required-ci` rejects skipped dependencies and requires all three current-run records. Start by selecting focused checks and ordering cheap failures earlier. Any later required-step selection needs conservative transitive ownership for shared UI/contracts/legal/toolchain/workflows, explicit unchanged-input evidence rules, and negative policy tests; do not turn path filtering into missing auth/tenant or packaged-image proof.

## Acceptance benchmarks and unknowns

Before adopting changes, compare cold and warm runs at identical source on matched runner classes: prerequisite network times, browser phase p50/p95, per-file setup/import/hooks/migrations, shard imbalance, image archive/native inventory/scanner phases, transfer sizes, total critical path and summed runner seconds. Require unchanged test inventory, no lost negative authorization cases, fresh-resource startup, exact build-identity reuse, redaction/provider audit and fail-closed source/runner/evidence/retention gates. Existing CMS build reuse and landing build reuse are already implemented; do not count them again as new savings. Standalone main timings were subsequently added above. No cache-hit experiment, browser-ready environment parity test, or sharded-DB benchmark was run for this report. Proposed runtime ranges are inferences and must not be added together as guaranteed savings.
